# AutoRouter improvement plan

Make routing dependable across long sessions, make every model decision understandable, and make setup and releases easier for software engineers to operate. Start with correctness and diagnostics, then optimize measured overhead and finish the CLI presentation.

This is a proposed implementation plan, reviewed on October 5, 2026 against version 0.3.7, commit `b377a8a`. It does not implement or release the changes below. The current checkout passes all 343 tests and the syntax check. GitHub CI and the publication workflow for this commit passed, npm identifies 0.3.7 as `latest`, and the repository has no open issues at review time. The audit used synthetic local reproductions and source inspection; it made no live evaluator or Claude inference calls.

Keep the existing Node.js CLI and gateway design, zero runtime dependencies, Jev default, and native `/v1/systemone` support for Ollama. Preserve Claude authentication and permission reviews, verbatim response forwarding, optional session logging disabled by default, and the distinction between API-equivalent savings and actual subscription savings. New human tasks must remain eligible for automatic model switching, including Sonnet/Opus switching in Auto mode.

The roadmap below uses engineering-day estimates for one engineer, including tests and review. These are planning estimates, not delivery commitments. Overall scope is approximately 19–27 engineering days; provider validation and review availability can extend elapsed time.

| Work | Priority | Estimate | Dependency |
| --- | --- | --- | --- |
| R1 Request compatibility and model facts | First | 2–3 days | Characterization fixtures from R3 |
| R2 Durable turn identity and confirmed models | First | 3–4 days | R1 and continuation fixtures |
| R3 Evaluation gates and integration contracts | First | 3–4 days | Start before behavior changes |

**R1 — Apply one compatibility policy across every routing profile.**

The final shared-capability target check is currently limited to Auto mode in [router.mjs](../src/router.mjs#L376). A synthetic compatible-profile request with forced tool choice can select Opus 5.5 while retaining that choice through [model-request.mjs](../src/model-request.mjs). Anthropic documents that request as invalid. This audit reproduced the generated request locally, rather than sending a known-invalid request to the provider. [Opus 5.5 restrictions](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5).

Create a shared model catalog containing exact IDs, routing family, input/output limits, thinking modes, tool-choice restrictions, Auto eligibility, and capability provenance with a review date. Keep pricing facts versioned alongside their sources. Routing, request adaptation, token counting, status context limits, and configuration should consume consistent facts. Introduce typed internal contracts and a pure compatibility decision function that returns a stable reason; keep transport and configuration separate from that decision.

Also validate the request structures AutoRouter actually consumes. For example, `tools: {}` currently passes the outer check in [server.mjs](../src/server.mjs#L157), throws inside routing, and becomes a misleading 502. Validate consumed shapes without rejecting or deleting unfamiliar provider extensions.

Acceptance: compatible, native, and Auto profile fixtures never transform a valid source request into a known-invalid target request. Cover forced tool choice, thinking, output limits, context edits, specialized tools, and unknown IDs. Malformed consumed fields return a bounded 400 before evaluator/upstream calls. Valid unfamiliar fields and signed history remain intact; retain the source model with an explicit reason when target compatibility is unknown. Existing successful three-tier and Auto switching scenarios continue to pass; broader checking must not silently pin all requests again.

**R2 — Separate active execution state from disposable classification caches.**

Turn pins use the same expiring/LRU cache design as classification decisions, with a 30-minute TTL in [config.mjs](../src/config.mjs#L113). A local reproduction expires an Opus pin and then routes its tool result back to a Haiku-compatible client's requested model with `unknown_continuation`. This is a continuity risk for long tools, approval waits, and cache pressure. See [router.mjs](../src/router.mjs#L299).

Define explicit requested, proposed, confirmed, and continuing model state, scoped by session, agent, and task. Retain active task identity independently of classification TTL while tools or approvals are pending, with bounded lifecycle cleanup. Define visible recovery for genuinely missing state after restart or eviction; a client model label is not proof of which model executed the previous turn. Deliberate capacity or compatibility changes remain possible and must explain why they override continuity.

Reconcile state with provider observations. [response-observer.mjs](../src/response-observer.mjs#L36) currently reports only the first model, while fallback blocks only make pricing unsupported. Support documented serving-model transitions and feed confirmed execution evidence back into the relevant turn state. [Anthropic fallback contract](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback).

Acceptance: fake-clock expiry, cache pressure, parallel agents, tool continuations, and `/goal` feedback cannot silently replace a known active model. Distinguish observing a serving model from committing successful continuation state. Cover fallback before output and midstream, cancellation/errors after `message_start`, and out-of-order concurrent attempts; failed or superseded attempts cannot overwrite valid execution state. Track which model produced an actionable tool call rather than assuming the final observed model produced every earlier block. Provider fallback updates the displayed serving model and appropriate continuation state, while preserving every response byte and permission verdict. A new human task can still switch both upward and downward. Unknown continuity is explicitly reported instead of presented as a known pin.

**R3 — Make a passing evaluation demonstrate the intended behavior.**

[live-validation.mjs](../scripts/live-validation.mjs#L401) reports evaluator success separately from its overall pass condition, so ordinary scenarios can pass on fallback alone. [evaluate.mjs](../scripts/evaluate.mjs#L27) fails on fallback but not on poor label agreement. These are useful connectivity reports, but incomplete routing-quality gates. Installed-package smoke tests also cover fewer profiles and lifecycle paths than the source tests. See [package-smoke.mjs](../scripts/package-smoke.mjs).

Add versioned synthetic Claude request/response fixtures covering Auto safeguards, thinking, deferred tools, compaction, goal feedback, provider fallback, and usage. Separate deterministic policy/transport tests from classifier quality and downstream task quality. Normal live checks must prove the configured evaluator worked; simulated-outage tests must explicitly expect fallback. Expand the held-out routing corpus with short difficult follow-ups, long trivial context, multilingual prompts, all three tiers, and attempts to influence tier selection through task text. Record acceptable tiers and an under-routing budget before evaluating a candidate.

Extend exact-tarball smoke tests to all profiles, synthetic subscription forwarding, streaming failures, cancellation, child startup failure, nonzero exits, SIGINT/SIGTERM, and cleanup. Package an explicitly invoked local evaluator diagnostic, tentatively `doctor --evaluate-local`, that reuses synthetic cases and reports cold/warm latency, verdict, deadline, and fallback cause. It must make no Anthropic/Jev calls, downloads, or configuration changes. Preserve the running Ollama service and unrelated resident models; report observed cold/warm conditions instead of silently unloading models to manufacture them.

Acceptance: intentionally broken routing, all-fallback normal runs, and missing tier coverage fail the appropriate gate. Require Haiku/Sonnet/Opus coverage for compatible routing and Sonnet/Opus coverage for Auto; constrained fixtures assert their expected override. Transport success, evaluator availability, rubric agreement, and independently tested task completion are reported separately. Reports include classifier choice, selected model, and confirmed model. Ordinary CI uses fake credentials and makes no real provider calls. Real-provider canaries are opt-in with bounded usage; they supplement deterministic regression coverage. Record a supported/tested Claude version range rather than accepting an executable version as evidence of full compatibility.

**R4 — Make changing and repairing configuration safe and obvious.**

[setup](../src/onboarding.mjs#L43) reconstructs settings from defaults, and `--force` replaces the saved file. The missing-model repair suggestion in [doctor](../src/onboarding.mjs#L152) omits the configured model, so following it can change a saved Tev1 setup to Nimble and replace unrelated preferences. Local checks also reproduced blank confidence values becoming zero, inactive-provider settings blocking the active provider, and `claude-autorouter claude --help` requiring router credentials.

Introduce deliberate configuration operations, tentatively `config show`, `config set`, and `config unset`. Normal updates merge only selected fields; explicit replacement remains available. Show the effective model mapping, evaluator, deadlines, profile, and default/file/environment provenance, with secret presence only. Validate numeric input strictly and validate the selected evaluator at runtime; an explicit full configuration check can report inactive-provider problems separately. Repair must use the exact configured model and preserve existing credentials and preferences. Downloading remains explicit.

Give each subcommand concise help and examples. Claude help/version passthrough should work without starting the gateway, preparing Ollama, creating temporary files, or requiring evaluator keys. Doctor should distinguish local configuration health, model availability, and actual evaluation results, with a specific next action for each failure.

Acceptance: changing a deadline or logging preference preserves unrelated settings; environment overrides are visible; secret values never appear in text or JSON output. Secret updates use hidden prompts or stdin and do not require credentials in command arguments or shell history. Blank numeric values fail with the setting name, while documented zero values retain their meaning. Existing configuration files remain readable. Repairing Tev1 pulls Tev1, and cancelling setup/repair leaves the previous configuration usable.

**R5 — Explain decisions and outcomes in the terminal and saved history.**

Persistent logs currently contain only the pre-forward decision from [server.mjs](../src/server.mjs#L182), so they cannot prove that the chosen model actually answered. Their [schema](../src/session-log.mjs#L25) also omits outcome and context-check details. At common narrow widths, [statusline.mjs](../src/statusline.mjs#L165) can remove the routing explanation while retaining savings. That makes a valid Sonnet floor or pin resemble a stuck evaluator.

Define one versioned, bounded event contract shared by status and optional logging. Preserve the existing decision record and add correlated outcomes: confirmed model or model transitions, safe error category, completion/cancellation, usage completeness, and pricing eligibility. Add bounded explanations for overrides and unpriced requests. Distinguish evaluation time, total routing time, and time to the first upstream response. Keep prompt excerpts behind the existing explicit logging choice; offer metadata-only history without broadening default collection.

Add local history commands, tentatively `sessions list` and `sessions show ID`, with readable and JSON output. Summarize model distribution, overrides, fallback rate, routing latency, failed requests, and API-equivalent savings coverage. Explain when history was not enabled. On narrow status lines, prioritize actual/selected model and error or guard reason before optional savings. Example target: `Sonnet 5.5 · Auto floor from Haiku · Jev 220ms`. Confirmation qualifiers must remain visible when the provider has not yet reported a model.

Acceptance: a log selection cannot be mistaken for successful inference; concurrent requests correlate correctly; old schema-1 decision files remain readable. Test widths of 40, 80, 100, and 120 columns, Unicode, color-disabled output, offline status, and missing usage. Logs remain optional, private, bounded in memory, and unable to fail inference. Any disk retention or cleanup policy requires an explicit setting. Savings identify their pricing version and unpriced coverage and remain clearly labeled as estimates.

**R6 — Reduce measured overhead while preserving routing semantics.**

Classification currently runs before known turn-pin handling in [router.mjs](../src/router.mjs#L273). Eight simultaneous identical synthetic classification requests produced eight evaluator calls because the cache holds completed results only. Jev response parsing lacks a response-byte limit in [router.mjs](../src/router.mjs#L201), although a deadline exists; Ollama already has a bounded reader. Status snapshots use synchronous filesystem writes in [status-state.mjs](../src/status-state.mjs#L39); their real latency impact is currently unmeasured.

First establish repeatable local benchmarks for small requests, large tool catalogs, cache hits, pinned continuations, concurrent agents, cancellation, and slow storage. Measure router-only p50/p95 latency, memory, evaluator calls, and event-loop delay separately from provider/model latency. Local-model benchmarks should include 16 GB and 24 GB-or-larger Macs with recorded background load and cold/warm conditions. Then coalesce identical in-flight evaluations, introduce a shared bounded response reader, and make status persistence asynchronous with atomic replacement.

After R2's policy is stable, evaluate reusing a prior classification for a known pinned continuation. This is an explicit change to the current evaluate-per-request behavior: every new human task must still be evaluated, and reused decisions must be labeled accurately. Do not skip compatibility or context-capacity checks. Changing cache keys to bounded classifier input requires accounting for evaluator configuration, rubric version, and requested capability floor.

Acceptance: concurrent identical work uses one evaluator request; cancelling one waiter does not cancel others; failures do not poison later attempts. Oversized or malformed evaluator responses produce the existing safe fallback and release resources. Stalled responses fall back when the configured deadline is enabled; `AUTOROUTER_OLLAMA_TIMEOUT_MS=0` retains its disabled-deadline behavior while user/disconnect cancellation and response-size limits remain active. A blocked status write cannot block a mocked inference stream. Shutdown cannot recreate deleted status files. Set numerical performance gates from the recorded baseline and representative hardware, rather than inventing a universal millisecond target; keep noisy network benchmarks outside ordinary CI.

**R7 — Treat npm acceptance and npm availability as separate release states.**

The workflow currently ends with [npm publish](../.github/workflows/publish.yml#L92). Version 0.3.7 needed manual follow-up while npm validated the submission and its metadata/tarball propagated. Existing archive checks and OIDC publication should be retained, with a shared verification helper replacing the version-specific scripts kept under local artifacts.

Before a stable release, verify the intended version is newer than the current stable `latest`; report registry failures separately from version availability. After submission, use bounded polling with backoff to verify the version, dist-tag, tarball integrity against the tested archive, and an isolated install. Expose submitted, validating/unavailable, verified, and failed states separately. Allow verification to be rerun independently of publication using the original immutable archive. Retrying a workflow must recognize an already-published identical version; it must never blindly republish or accept different bytes.

Acceptance: mock delayed metadata, delayed tarballs, cached 404s, existing versions, integrity mismatches, and newer stable releases. A timeout reports pending verification and retains the artifact; it does not assert publication failure or prompt a duplicate release. A later valid release must not be overwritten merely to restore an older `latest` tag. Release notes and downloadable canonical archives are retained, and the documented upgrade command works from the public registry before the release is marked verified.

**R8 — Keep documentation and contributor checks aligned with the product.**

The README currently mixes the first-run path with detailed migration and benchmark history. Preserve that information in the reference/evaluation documents while shortening the common paths: install, configure Jev or Ollama, select Auto mode, inspect a decision, and troubleshoot a fallback. Document the configuration and history commands introduced above, plus upgrades and the tested Claude compatibility range. Describe data flow and API-equivalent savings near the relevant choices.

Add a contributor guide for the request lifecycle, state ownership, model-fact updates, evaluation fixtures, and release verification. [check.mjs](../scripts/check.mjs) currently checks syntax only. Add development-time contract checks for configuration, decisions, and events, plus a consistent formatting/lint policy, while retaining zero runtime dependencies. Review capability and pricing sources on model updates; changing provider behavior should require a dated catalog update and regression fixture, not scattered edits across routing, display, and accounting.

Acceptance: a new engineer can follow each documented path using the installed package; help and documentation agree; examples are exercised by package smoke tests. A model update has one documented checklist and one source of maintained facts. Static checks catch incorrect event fields before runtime. The review itself introduces no new automatic network checks or silent model-default updates at launch.

Deliver the work in three reviewable milestones. First, add the failing characterization fixtures and complete R1/R2 correctness fixes, the critical R3 gate changes, and R7 release verification. Small configuration validation/help fixes can proceed in parallel. Second, ship the remaining R4 setup/repair work, the local diagnostic, R5 explanations/history, and their documentation together. Third, use measured baselines to finish R6 optimizations and the remaining R8 contributor/static-check work. Release correctness fixes in a patch when independently ready; group new CLI interfaces and event-schema evolution into a subsequent minor release.

Each implementation PR should identify the observed problem, its focused acceptance tests, changed behavior, and migration impact. Run syntax/static checks, the full regression suite, and exact-tarball package checks before a release. Paid canaries require deliberate invocation and separately reported results. Completion of this roadmap requires evidence for every acceptance criterion above; a green connectivity check or a prettier status line alone does not establish routing quality.
